## 1. Как улучшили работу ассистента (Слой A — «как я работаю»)

**Было:** после детекта профиля задачи ассистент спрашивал подтверждение («Определил профиль X,
верно?»), а перед реализацией часто показывал план на утверждение. «Ловцом ошибок» по факту был
пользователь — каждый шаг возвращался к нему на подтверждение. Это тормозило и конфликтовало:
чем автономнее ассистент, тем больше риск, что он «уедет не туда», раз проверяет только человек.

**Стало — `autonomous-run` по умолчанию + машинные гейты качества:**

| Что изменилось | В чём польза |
|---|---|
| **Детект профиля → объяви строкой и продолжай**, без вопроса на подтверждение | Меньше round-trip'ов; вопрос — только при реальном конфликте детекта или в security-профиле |
| **Plan Mode — только когда действительно нужен** (границы систем, Слой B/промпты, security, размытая постановка) | Рутинные задачи (≤~3 файла, чёткая постановка) идут сразу по цепочке профиля |
| **Качество держат встроенные гейты, а не пользователь:** `Review=PASS`, DoD агентов, hooks | «Ловец ошибок» стал машинным — автономность и качество растут вместе, а не конфликтуют |
| **Оркестратор не читает код для маршрутизации** — только карты (`CLAUDE.md`/`PLAN.md`), `ls`, `git status` | Контекст-окно не забивается; понять код = отдельный агент, который вернёт короткий дайджест |
| **Блок «Автономность» в промптах persona-агентов** | Агент сам решает развилки реализации по инвариантам, эскалирует только security/необратимое |
| **Hook-гейт `/code-review` перед commit** (`.claude/hooks/review-gate.sh`) | Ревью перед коммитом срабатывает принудительно, а не «если модель вспомнит» |

Итог: типовая задача идёт `детект → работа → Review=PASS → фиксация` без остановок на подтверждения,
но с жёстким машинным контролем качества на выходе. Пользователь подключается там, где реально нужно
его решение (security, необратимое, бизнес-развилка), а не на каждом шаге.

## 2. Как починили авто-ревью PR (GitHub Action)

**Симптом:** на большом PR #6 авто-ревью выдавал ложное `[critical]`-замечание и не предупреждал,
что судил по обрывку diff.

**Причина — «двойное усечение»:** GitHub-workflow резал diff `head -c 100000` (100 КБ), и ровно
такой же лимит (100 КБ) стоял на backend (`Field(max_length)` и `truncate_diff`). Из-за совпадения
лимитов флаг «diff был обрезан» **никогда не мог стать `True`** — а значит честная пометка
«показаны замечания только по видимой части» в отчёте была мёртвым кодом. Модель ревьюила урезанный
diff и уверенно выдавала находки, будто видела его целиком.

**Что сделали:**

- **Workflow шлёт diff целиком** (аварийный потолок `head -c 2 МБ` — только против гигантских
  бинарных дампов, это не бюджет LLM). Решение об усечении и честную пометку теперь принимает
  один хозяин — backend.
- **`_DIFF_LIMIT` (200 КБ) выводится из реальных констант бюджета** контекста модели (128K токенов),
  а не задан «на глаз», с `assert` на импорте — если кто-то раздует смежные лимиты, сборка честно
  упадёт с понятной причиной, а не молча переполнит контекст.
- **Хард-лимит запроса (2 МБ) отделён от мягкого бюджета LLM (200 КБ)** — иначе Pydantic отбрасывал
  бы diff 422-й ошибкой ещё до того, как сработает аккуратное усечение с пометкой.
- **+2 регресс-теста:** diff в новом лимите проходит без усечения; diff за лимитом усекается и
  ответ честно предупреждает об этом.

Итог: авто-ревью либо видит весь diff, либо **честно сообщает**, что показал замечания только по
видимой части — пользователь больше не примет находку по обрывку diff за полную картину.

### 2.1. Сравнение ревью: до и после улучшений

| Аспект | Было (до) | Стало (после) |
|---|---|---|
| **Охват diff** | Двойное усечение 100 КБ (workflow + backend), лимиты совпадали | Весь diff идёт в один LLM-вызов; усечение — только на backend при >200 КБ |
| **Пометка об усечении** | Мёртвый код: флаг «diff обрезан» **никогда** не мог стать `True` | Флаг реально срабатывает — в комментарии честная пометка «замечания только по видимой части» |
| **Бюджет вывода** | 2048 токенов → JSON-ответ обрезался на больших PR (находки терялись) | 8192 (retry 16384), выведен из констант модели с `assert` |
| **Постинг комментария** | PATCH одного комментария (перезапись, история push теряется) | Новый комментарий на каждый push, помечен `HEAD_SHA` — видна динамика |
| **Ложные `[critical]`** | ⚠️ **всё ещё возможны** — напр. «SyntaxError» на файле, который чисто компилируется | ⚠️ **пока не закрыто** — верификационный гейт (`ast.parse`/`py_compile`) занесён в `PLAN.md` (Этап 3c, «Отложено») |

**Как читать колонку «Ложные critical».** Диагностический разбор 2026-07-26 показал: критическая
находка ревью может быть ложной **не** из-за чанкинга (ревью идёт одним вызовом на весь diff —
дробления нет). Реальная причина — обычная галлюцинация LLM-ревьюера, усугублённая тем, что барьер
секретов `redact` подставляет `[REDACTED]` в diff, и модель читает это как оборванный строковый
литерал → уверенно рапортует `SyntaxError` с неточной привязкой к строкам. Такие заявки машинно
проверяемы, поэтому фикс — не «просить модель быть аккуратнее», а поставить машинный гейт (см.
`PLAN.md`). Это тот же принцип, что и в блоке 1: **ловца ошибок делаем машинным, а не человеком.**
