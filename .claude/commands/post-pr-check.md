# /post-pr-check — единый QA-цикл после PR

Ты — QA-оркестратор jWorkPlace. Прогоняешь **оба уровня тестирования** и собираешь **один
отчёт**. Оба уровня — из задания «два уровня тестирования» (см. `PLAN.md` / это задание).

Аргумент: `$ARGUMENTS`

## Когда запускается
- Вручную после открытия/мержа PR (напоминает hook `post-pr-smoke.sh` после `gh pr create`).
- С флагом `--refresh` — сценарий «я задеплоил новую фичу»: сперва **обнови smoke-сценарии**
  под изменения фронта, потом гоняй всё заново.

## Шаги

### 0. (Только при `--refresh`) Обнови smoke под новую фичу
1. `git diff --stat origin/master...HEAD -- frontend/src` — что изменилось в UI.
2. Если появились/изменились панели, кнопки, флоу — обнови/добавь спеки в `frontend/e2e/*.spec.ts`
   и текстовые сценарии в `swarm-report/level2-smoke-report.md` (раздел «Сценарии»).
3. Проверь стенд в `frontend/playwright.config.ts`. По умолчанию smoke гоняется против **локального
   dev-сервера** (`baseURL http://localhost:5173`, `webServer: npm run dev`, proxy `/api → :8200`) —
   локальный backend открыт и держит актуальную (в т.ч. не задеплоенную) сборку. Прод
   `https://jwork.jorchik.com` `/api/*` под Bearer (401 без токена) — для смоука не цель.

### 1. Level 1 — код-тесты
```bash
cd backend && python -m pytest -q
cd ../frontend && npx vitest run
```
Зафиксируй: сколько passed/failed по каждому раннеру.

### 2. Level 2 — UI-smoke через Playwright
```bash
cd frontend && npx playwright test
```
Скриншоты по шагам — в `frontend/e2e/screenshots/`. Зафиксируй вердикт по каждому сценарию.
Если Playwright browsers не стоят — `npx playwright install --with-deps chromium`.

### 3. Сводный отчёт
Собери `swarm-report/<branch>-qa-report.md` по шаблону `swarm-report/TEMPLATE-qa-report.md`:
- Итог Level 1 (pytest + vitest): N passed / M failed.
- Итог Level 2: таблица «сценарий → PASS/FAIL → ссылка на скриншоты».
- **Если что-то упало** — по каждому падению укажи **предполагаемое место проблемы**
  (`file:line` / селектор / фича не задеплоена / auth-гейт / сеть), не просто «упало».
- Общий вердикт: 🟢 всё зелёное / 🔴 есть падения (перечисли).

### 4. Эскалация
Если падение — это реальный баг продукта (не флейки тест) — предложи завести задачу
в профиле **P2 (Баг)** с находкой как входом. Сам код продукта здесь не чини — это QA-гейт.

## Инварианты
- Код-тесты **офлайн** и детерминированы (без реальных LLM/git/Ollama — всё замокано).
- Smoke не должен спайкать RAM (не запускай тяжёлую индексацию больших репо; для «создать
  сущность» — минимальный репо + удаление за собой).
- Ничего не коммить в этой команде без явного запроса — это проверка, не Ship.
