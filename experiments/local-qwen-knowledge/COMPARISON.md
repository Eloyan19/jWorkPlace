# Сравнение: Claude (PR #10) vs локальная qwen2.5-coder:3b

Эксперимент 2026-07-27. Одна и та же задача поставлена двум исполнителям — облачному Claude
(через оркестрацию jWorkPlace) и **локальной** модели на VPS. Цель — увидеть, где проходит
граница возможностей маленькой локальной модели на реальной многофайловой фиче.

- **PR Claude** (эталон): #10 — `feat(knowledge): ручная «Изучено» + «Очистить базу знаний»`.
- **PR локальной модели**: этот PR — код перенесён **дословно** из вывода `jwp-qwen`, с её
  решениями и её дефектами, **без правок за неё** (иначе сравнение потеряло бы смысл).

---

## Как настроена локальная модель

Изначальный план (PR #11) — поднять модель в IDE на своей машине — не завёлся, поэтому гоним
модель **прямо на VPS** через Ollama, без IDE/автокомплита (для работы с VPS они не нужны).

- Модель: `qwen2.5-coder:3b` (instruct, 1.9 ГБ). Потолок VPS — RAM 3.8 ГБ → модели ≤3B;
  рекомендованная гайдом `7b` не влезает.
- Конфиг (Modelfile `jwp-qwen`, см. `Modelfile.jwp`) — перенос параметров «Чат/правки» из PR #11
  на CPU-инференс:
  - `num_ctx 8192` (гайд советует 16384, но на 3b + 3.8 ГБ держим 8192 — KV-cache уходит в RAM),
    `temperature 0.2`, `top_p 0.9`, `top_k 40`, `repeat_penalty 1.05`, `num_predict 2048`.
  - `SYSTEM` = дистиллят `.continue/rules/*` (глобальные + backend + frontend правила проекта) —
    аналог того, как Continue грузит правила из репо.
- Запуск: `ollama run jwp-qwen < task-prompt.txt` — **533 с (~9 мин) на CPU**, модель заняла 2.4 ГБ.
- В промпт (`task-prompt.txt`) вручную вложены релевантные куски кода — имитация `@file`, т.к. у
  голой модели нет RAG-индекса jWorkPlace (в этом и суть продукта: grounding по индексу vs
  «видит только показанное»).

## Где именно локальная модель «сломалась»

1. **Потеряла ядро фичи.** Требование №1 — кнопка «Изучено» на каждом новом концепте с
   оптимистичным переносом в «Уже знакомо» — просто отсутствует. Модель сделала только более
   простую кнопку «Очистить базу знаний». `markConceptKnown` в `api.ts` она добавила, но **нигде
   не вызвала** — мёртвый экспорт.
2. **Проигнорировала «убрать авто-пометку».** Старый авто-вызов `markSummaryRead` при открытии
   панели остался — то есть баг, ради которого фичу и делали, не устранён.
3. **Грубая перезагрузка.** `window.location.reload()` вместо мягкой перезагрузки выжимки —
   теряет всё состояние страницы, против SPA-конвенций проекта.
4. **Нет защиты от гонок/ошибок.** Хендлер `await resetKnownCatalog()` без try-catch и без
   `mountedRef`/`activeIdRef` — прямое нарушение правил фронта, которые лежали в её system-промпте.

## Что она сделала хорошо

- **Механический плюминг — точно.** `slug` протянут через SELECT → render → DTO → тип; эндпоинты
  и api-обёртки написаны по конвенциям (относительные URL, `authHeaders`, `to_thread`, `HTTPException`).
- **Формат вывода** — код по файлам, минимум прозы; ровно как просили её правила.
- **Удачная догадка** про `db.get_concept_by_slug` — функция реально существует (`db.py:510`),
  хотя в контекст её не давали.

## Вывод

`qwen2.5-coder:3b` локально **годна для узких, чётко заданных правок** (добавь функцию, протяни
поле, напиши эндпоинт по образцу) — механику и конвенции держит. Но **многофайловую фичу с
UX-логикой и удержанием списка требований целиком не тянет**: теряет главный пункт ТЗ, не
доводит связку frontend↔backend, срывается на анти-паттернах. Это ровно та граница, ради которой
jWorkPlace даёт grounding по индексу и оркестрацию, а не «одну модель в чате».

**Оговорка о честности сравнения:** контекст модели я резал вручную под задачу — это приближение.
Полностью равный матч был бы через реальный Continue + `@codebase` на машине пользователя, но
именно это и не завелось; прогон на VPS — ближайшая доступная замена.
