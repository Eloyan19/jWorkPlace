# routing — маршрутизация запросов между моделями с fallback

Учебный сайдкар: **дешёвая модель отвечает первой, сильная — как fallback по эвристике «не уверен →
эскалируй»**. Задача та же, что в соседнем треке `confidence` (классификация тикетов поддержки
jWorkPlace), но здесь мы не просто оцениваем уверенность, а **направляем** запрос: остаться на
`deepseek-v4-flash` или эскалировать на `deepseek-v4-pro`. Не трогает `backend/app/` — самостоятельная
папка, HTTP-ядро/ключ/схему/confidence-пайплайн переиспользует из `../confidence/confidence_harness.py`.

## Три эвристики эскалации (от дешёвой-слепой к дорогой-сильной)

| Эвристика | Что смотрит | Цена пробы | Ловит |
|---|---|---|---|
| `length` | длина/усечённость ответа flash | 1 вызов flash | пустой/обрезанный вывод |
| `constraint` | валидность строгой JSON-схемы | 1 вызов flash | формат-брак (не та схема/мусор) |
| `confidence` | статус OK/UNSURE/FAIL + порог `agreement` (полный self-consistency + self-check пайплайн) | 3–4 вызова flash | семантическую неуверенность |

Все три — чистые функции над собранными сигналами (`router.policy_*`). Fallback выполняет
`router.route(policy, signals)`: при эскалации ответ берётся у `pro`, иначе у `flash`; стоимость
считается честно — только вызовы, которые эта политика реально сделала бы (своя проба + `pro` при
эскалации), см. `router.route`.

## Как это устроено (методология прогона)

`run_routing.py` для КАЖДОГО входа один раз собирает три сигнала — одиночный ответ `flash`, полный
confidence-пайплайн `flash`, одиночный ответ `pro` — и затем **просчитывает все три политики по этим
общим сигналам** (без новых вызовов). Так эвристики судят по идентичным ответам моделей: разница в
метриках идёт от решения о роутинге, а не от разброса сэмплинга. (Из-за этого измерение делает больше
вызовов, чем любая одна политика в проде; «стоимость политики» в отчёте — только её собственные вызовы.)

## Запуск

Ключ — в `../../backend/.env` (`DEEPSEEK_API_KEY`), подхватывается сам (парсингом файла, без импорта
`backend.app`). Модели можно переопределить правкой `router.SMALL_MODEL`/`BIG_MODEL`.

```bash
cd experiments/routing
../../backend/venv/bin/python3 run_routing.py          # реальный прогон → report.md
../../backend/venv/bin/python3 -m pytest tests/ -q     # юнит-тесты логики (без сети)
```

Прогон — 20 входов × (1 flash + confidence-пайплайн ≤4 flash + 1 pro) ≈ до ~120 вызовов. Нет ключа /
API недоступен → скрипт НЕ выдумывает числа, помечает в `report.md`, что прогон не выполнен, и
выходит с кодом 1.

## Как читать `report.md`

1. **Роутинг** — сколько входов каждая эвристика оставила на flash / увела на pro (+ разбивка по
   корзинам correct/borderline/noisy).
2. **Точность** на корзине `correct` (есть gold): `всё на flash` vs `всё на pro` vs `routing по X` —
   виден ли прирост качества от fallback.
3. **Стоимость**: те же три конфигурации в `$` и вызовах — виден trade-off силы сигнала против цены
   (confidence дороже даже без эскалаций, т.к. сама проба = 3–4 вызова).
4. **Построчно** — решение каждой эвристики по каждому входу (`flash`/`🔺pro` + причина).
5. **Выводы** — плюсы/минусы эвристик и почему разумный прод-выбор — каскад (дешёвые фильтры всегда,
   дорогую confidence-пробу — выборочно).

## Ограничения

- Прайс в `router.PRICE` — **приблизительные** placeholder-константы (особенно `pro`); точный
  биллинг/cache-hit не учитываются. Относительный вывод (routing дешевле, чем всё гнать на `pro`)
  держится, пока `pro` дороже `flash`.
- Тест-сет мал (20 строк, общий с треком `confidence`) — числа показывают направление, не строгую
  статистику.
- В `response_format=json_object` `flash` почти всегда возвращает валидный непустой JSON, поэтому
  дешёвые эвристики (`length`/`constraint`) на «здоровом» наборе срабатывают редко — это и есть их
  честный минус, а не баг прогона.
