# decomposition — декомпозиция инференса (monolithic vs multi-stage)

Учебный сайдкар: одну и ту же задачу — **полный триаж тикета поддержки jWorkPlace** — решаем двумя
способами и сравниваем на реальном DeepSeek.

- **Вариант A — monolithic:** ОДИН большой запрос → один JSON из 9 полей (нормализация + отбивка
  prompt-injection + классификация + вычисление маршрута по условиям — всё сразу).
- **Вариант B — multi-stage:** цепочка коротких дешёвых этапов со строгим форматом каждого:
  1. `stage1` (LLM) — нормализация/разметка сырого входа → `{lang, on_topic, injection_attempt, clean_summary}`;
  2. `stage2` (LLM) — классификация уже ЧИСТОЙ сути → `{category, priority}`;
  3. `decide()` (**чистый код, 0 вызовов**) — маршрут по условиям → `{team, sla_hours, needs_human, action}`.

> Полное объяснение теории, терминов и «когда что применять» — в [`EXPLAINER.md`](./EXPLAINER.md).
> Это главный учебный артефакт трека; начни с него.

Не трогает `backend/app/` — самостоятельная папка. HTTP-ядро, парсинг ключа, строгую схему
`{category, priority}` и прайс переиспользует из соседнего `../confidence/confidence_harness.py`
(тот же паттерн секретов: `DEEPSEEK_API_KEY` из env/`backend/.env`, НИКОГДА не логируется и не в промпт).

## Задача — почему она «плохо решается одним запросом»

Триаж совмещает три вещи из ТЗ сразу: **сложную классификацию** (6 категорий), **извлечение
нескольких полей** (язык, флаги, приоритет) и **принятие решения по условиям** (маршрут зависит от
категории+приоритета+флагов). Вход бывает шумным (транслит, эмодзи, обрывки) и враждебным (внутри
тикета — prompt-injection). Один запрос заставляет модель жонглировать всем сразу — тут и видно
разницу подходов.

## Как устроено

- `pipeline.py` — ядро: `decide()` (детерминированные правила), строгие валидаторы формата
  (`validate_stage1`/`validate_stage2`/`validate_monolith`) и два async-варианта (`run_monolith`,
  `run_multistage`). Все функции решения — чистые, тестируются без сети.
- `run_decomposition.py` — прогоняет ОБА варианта по каждому входу и пишет `report.md`.
- `data/` — `test_inputs.jsonl` (20 тикетов: correct/borderline/noisy, общий с треками
  confidence/routing) + три промпта (`monolith_prompt.txt`, `stage1_prompt.txt`, `stage2_prompt.txt`).
- `tests/test_pipeline.py` — юнит-логика (схемы, `decide`, короткое замыкание, fail-closed) на
  замоканном HTTP-ядре, без сети.

## Запуск

Ключ — в `../../backend/.env` (`DEEPSEEK_API_KEY`), подхватывается сам (парсингом файла, без импорта
`backend.app`).

```bash
cd experiments/decomposition
../../backend/venv/bin/python3 run_decomposition.py          # реальный прогон → report.md
../../backend/venv/bin/python3 -m pytest tests/ -q           # юнит-логика (без сети)
```

Прогон — 20 входов × (1 монолитный вызов + цепочка 1–2 вызовов). Нет ключа / API недоступен → скрипт
НЕ выдумывает числа, помечает это в `report.md` и выходит с кодом 1.

## Как читать `report.md`

1. **Точность классификации** на корзине `correct` (есть gold): A vs B — роняет ли декомпозиция качество.
2. **Формат-надёжность** — сколько ответов невалидны по строгой схеме (у A рвётся весь ответ, у B —
   локальный этап; `decide()` не ломается — это код).
3. **Устойчивость к инъекции/шуму** (корзина `noisy`) + отдельный тест на утечку инъекции.
4. **Детерминизм маршрута** — соблюдены ли правила team/sla (у B гарантированно — код).
5. **Цена / латентность / вызовы** — честный trade-off (на равной модели B НЕ дешевле).
6. **Построчно** и **Выводы** — когда моно, когда декомпозиция.

## Ограничения

- Прайс в `confidence_harness.PRICE_*` — **приблизительные** placeholder-константы; относительный
  вывод (A и B почти равны по цене на одной модели) держится, точный биллинг — нет.
- Тест-сет мал (20 строк) — числа показывают направление, не строгую статистику.
- Обе ветки в этом прогоне на одной модели (`flash`) НАРОЧНО: так разница идёт от способа
  (моно vs декомпозиция), а не от модели. «Разные модели по этапам» — концептуально в `EXPLAINER.md`
  (архитектура это уже позволяет: `run_multistage(model_stage1=…, model_stage2=…)`).
